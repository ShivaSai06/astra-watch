Why I built Astra Watch

Managing multiple development machines and self-hosted services often means switching between terminal commands, Docker tools and different monitoring views just to understand what's happening.

I ran into this with my MacBook and a remote Linux server running several Docker-based workloads. When a machine got slow or a container started eating resources, I had to look at CPU, memory, disk space, running processes and container status separately. Checking the server meant connecting to it and running commands by hand.

I wanted a simpler way to answer a few questions:

  • Are my machines online and healthy?
  • What is using the CPU and memory, and which processes or containers are the heaviest?
  • Are there disk or container problems?
  • Has a device stopped reporting?
  • Can I check all of this securely while I'm away from my computer?

So I built Astra Watch: a small monitoring application that puts system metrics, process visibility, Docker monitoring and alerts into one private dashboard. It watches a local and a remote machine, keeps the last 24 hours of history, and sends Telegram notifications. Remote access goes through a private Tailscale network instead of the public internet.

I built it to solve a problem I actually had. It is a personal project, not a product, but other developers and self-hosters are welcome to read it, learn from it and extend it.

What it does

Everything below is implemented and in daily use on my own machines.

Multi-device monitoring

A MacBook (through a small agent) and a Linux server (collected locally), side by side. Each shows Connected, Stale or Offline, with a last-seen time.

CPU and memory

Current usage, load, memory pressure and 1-hour / 24-hour trend charts.

Disk and swap

Free space, how fast it is shrinking, and swap that keeps growing.

Process visibility

Top processes by CPU and memory. On the Mac, development workloads such as Node and test workers are grouped.

Docker containers

Status, health, restarts, CPU, memory, log size and Docker disk usage per container.

Alerts and incident history

Problems must last a few minutes before they alert, then show cause, impact and a suggested action. Recovered incidents stay for 24 hours.

Telegram notifications

One message per incident (no repeat spam), plus a "cleared" message when it recovers.

Private access with Tailscale

Reachable only from my own tailnet, over HTTPS, limited to one identity. Funnel is off.

Controlled stop actions

A runaway container can be stopped only after an explicit confirmation. Nothing is stopped automatically.

Architecture

A small agent on the Mac sends metrics to a backend on the server. The same backend watches the server itself, stores 24 hours in SQLite, evaluates alerts and talks to Telegram. Tailscale is the only way in.

Mac agent

Samples the Mac every 30 seconds and sends it to the backend with its own bearer token, stored in the macOS Keychain. launchd keeps it running.

Hetzner backend

Receives Mac data, reads /proc and Docker for the server's own metrics, runs the alert rules and serves the dashboard.

SQLite

One file with samples, snapshots and incidents. Anything older than 24 hours is deleted.

Tailscale

Makes the server reachable only from my devices, with an HTTPS certificate, and tells the backend who is asking.

Telegram

Receives alert messages and sends back Stop / Confirm taps, which the backend polls for.

Read the details in the architecture document.

Security and privacy

The real Astra Watch dashboard is private. This page is a separate static site and does not talk to it.

Not on the public internet

The live dashboard is only reachable from my own Tailscale network. Tailscale Funnel is disabled and the backend listens on localhost only.

Private access plus a login check

Being on the tailnet is not enough: the backend also requires the one authorised Tailscale identity, and CSRF tokens for changes.

Separate credentials

The Mac agent has its own revocable token (only its hash is stored on the server). Telegram is limited to my user and chat id.

Stop needs confirmation

Stopping a container is a two-step, single-use, time-limited approval for that exact target. Only docker stop is allowed.

More in security.md.

Status and limitations

Working

Two-machine monitoring, Docker visibility, alerts, Telegram, Tailscale access, controlled stop, 24-hour retention, one-command deploy with automatic rollback.

Limitations

Exactly two machines (a Mac and one Linux server), one owner, 24 hours of history, and it cannot alert you if the server itself is off.
